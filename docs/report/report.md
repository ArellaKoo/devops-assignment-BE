## Q3 — Where role and scope enforcement live

All persona Blueprints share two helpers in `app/auth.py`: `current_user()` resolves the Bearer token into a trusted `User` — refusing 401 when the header is missing or malformed, the token was not signed with the configured secret, it is past its 3,600-second life (exactly 3,600 s still verifies), or its id matches no stored account — and `require_role()` raises 403 before any controller body runs when the role does not match. A role answer is not a scope answer: every scoped read and mutation in `app/models/` takes the actor and checks the relationship itself — `Vendor.authorizes`, `MenuItem.authorizes_vendor`, the cart owner check in `Cart.set_item`, `Order.get_for_diner`/`get_for_vendor`/`can_transition` — raising the same 403/409 codes whichever persona made the request; the actor always comes from the verified token and the record always from a model query scoped to that actor. The lifecycle guard lives in `Order.transition_to`, the single guarded path any caller must use: it re-checks role, stall ownership, current state, the five permitted edges and the 30-minute no-show boundary, then persists with an expected-current-state update so two racing vendors cannot both apply a move; the routes only translate the request and map the model's `DomainError` codes to the JSON error contract.

## Q4 — Test suites: what the mocks can and cannot say

**Q4(a) — which methods the offline tests actually exercise.** The offline suite (302 tests, socket-sentinel-guarded, run with MongoDB stopped) supplies records and stubs only the persistence boundary; the named methods run for real. `Order.transition_to` runs for real in `tests/unit/test_order_guard.py`: every one of the 36 state pairs, the 29:59/30:00/30:01 no-show boundary with an injected clock, the actor/scope refusals, and the expected-current-state update semantics (the race case records the exact update and filter, and the 0-modified lost race proves `invalid_transition` without moving the local document). `Order.place_from_cart` runs for real for the stored-key replay, cart revalidation, fingerprint comparison, snapshot construction and cart clearing; only `find_by_checkout_key`, `save` and the cart write are supplied. What the mocks cannot say is stated rather than claimed: asserting that a fake `list_for_diner` returns the rows the test told it to proves nothing about owner filtering, `status__in` semantics or newest-first ordering in MongoDB — those behaviours are driven through `GET /api/diner/orders?view=current|history` in the real-database suite against documents that only the database wrote, and the checkout key's unique-index behaviour is proven only by the functional suite's concurrent checkout against the real index.

**Q4(b) — two concrete strengths of the assessed suites.** First, actual token/route/model integration rather than canned records: the functional tests never inject users — `User.create` writes a real hashed account, `POST /api/user/gettoken` must verify it and mint a signed 3,600-second token, and every subsequent request carries that token through `current_user()` → `require_role()` → the model scope check; no step of that chain exists in the unit suite, which patches `User.find_by_id`. `test_diner_and_vendor_complete_order` walks Pending→Preparing→Ready→Collected with two separately signed tokens and asserts both the HTTP response and the diner-visible state after each vendor move — an end-to-end sequence the offline suites, which supply the actor directly, structurally cannot contain. Second, real database references, updates and fixture isolation: the two-thread same-key checkout hits the real `(diner, checkout_key)` unique index — exactly one request stores the order (201), the other returns the stored order as a replay (200), and `Order.objects(checkout_key=...).count() == 1` is read back from MongoDB, not from a mocked collection; the stale-checkout cases prove no order row was inserted for each refused key; the snapshot test re-reads the stored order after the menu item was renamed and re-priced. Fixture isolation is real: the conftest refuses the development database name before any connection, registers every created document, sweeps route-created carts and orders by reference, and releases the MongoEngine alias after each app — which is why the suite was run twice against the same guarded `skipq_test` database (10 passed each time) with no manual reset between runs, leaving zero documents after each run.

## Q5 — Frontend architecture and flow evidence

The frontend is CRA with React Router 6; all routes live in `src/App.js` under a `RequireRole` gate and a persona layout that renders the shared feedback banner plus the outlet (route table in `docs/report/frontend-architecture.md`). The five shared decisions, each with the alternative it was weighed against and what it does not provide: (1) `src/config.js` — one configured API base URL matching the backend's CORS allowlist, so a fresh clone works from `.env.example`; no runtime discovery. (2) `src/api/client.js` — one fetch wrapper and one typed `ApiError` from the backend's stable error contract, native fetch rather than axios (its interceptor/retry features are unused), so token attachment and refusal parsing happen in exactly one place. (3) `FeedbackContext` + `FeedbackBanner` — a refusal raised on one screen survives a client-side redirect and lands where the user is; not a global toast system (no expiry timers, deduplication or translations). (4) `RequireRole` — a client-side gate that is explicitly not a security boundary: the backend re-verifies the token and role on every request (verified live: a diner's token was refused 403 on `GET /api/vendor/menu` while the UI kept running). (5) `AsyncButton`/`useAsyncAction` — a UI-side duplicate control for this tab's own clicks; a second tab, a second browser or a network-level resend is invisible to the button and is handled at the database layer instead, where the unique index makes a repeated checkout store at most one order, a matching replay returning the stored order and a conflicting reuse refused.

The flows: diner **Login → Stalls → Menu → Cart → Checkout → Tracking**, vendor **Login → Menu → (item form) / Orders → Order detail**. Sold-out and closed state are visible before the diner can act; the checkout key is minted when the page loads and retained across retries of the same attempt; the stale-cart refusal screen offers Review / Refresh-and-retry; and the vendor's order-detail controls render strictly from the response's `allowed_actions`, so the 30-minute no-show rule is visible in the UI, not only enforced by the backend. US10 reuses the Order List and Order Detail screens — no new history page: the list gains the All/Current/Past filter (Past never polls, because terminal orders cannot change), and the detail screen already renders terminal orders read-only with their notices. Flow evidence: `docs/report/q5-flows.md` (the two-context live verification paragraphs) and `docs/evidence/screenshots/` — `task8-01…18` (diner flow), `task9-01…27` (vendor flow), `task10-01…08` (US10 filters), `task11-01…11` (the two-persona lifecycle run).

## Q6 — Browser-versus-functional result and load verdict

**Q6(a) — the browser result the functional suite cannot establish.** The Playwright suite signs the diner and the vendor in through the real login screen in two isolated browser contexts — no token is injected into either browser. The diner clears the seeded cart, adds one item and checks out through the screen that mints the checkout key itself; the paid screen displays the new queue number, and the vendor's polling queue surfaces that exact number before Accept, Mark ready and Mark collected on the vendor's screens. After each transition the diner's tracking screen — polling on its own timer in the other context — is observed to display Preparing, then the Ready-for-collection notice, then terminal Collected. An in-process functional test cannot establish this: the Flask test client does not render React routing or DOM banners, does not exercise the checkout key the UI mints, and cannot show two independently polling browsers converging on the persisted state. Run 1 passed in 12.02 s and run 2 in 11.48 s against the same seeded guarded database, no reset between runs (`docs/evidence/browser-lifecycle/run-1.log`, `run-2.log`; screenshots `task11-01…11`).

**Q6(b) — endpoint, load and measurements.** The endpoint loaded is the UI's 3-second menu poll, the most frequent diner request; order placement and checkout are once-per-order events and were deliberately not loaded. Locust ran at the polling cadence (2.9–3.1 s wait) with one sign-in per user plus a separate repeated-sign-in probe; main run: 10 users, 2 users/s, 120 s, on a local M3 MacBook Air (8 cores, 8 GiB, macOS 26.6.2), the Flask development server, MongoEngine 0.29.3 / PyMongo 4.18.2, MongoDB 8.0.32 on loopback, and the seeded dataset of 6 users / 2 vendors / 5 menu items / 9 orders, after a 5-user/60 s sanity run. Result: **395 menu requests, 0 failures** — p50 5 ms, p95 20 ms, p99 65 ms, max 89.7 ms, 3.31 req/s; the 40 sign-ins were also 0 failures. Opt-in server-side instrumentation records that each menu request issues exactly three finds — `users` (1 row), `vendors` (1 row), `menu_items` (3 rows) — with server-reported find durations p50 0.36 ms / p95 1.19 ms and full menu-list materialisation p95 2.01 ms (`q6-performance/run-metadata.md`).

**Database verdict (≤100 words).** At 3.31 req/s, the menu endpoint's three finds — including `MenuItem.list_for_vendor` returning 3 rows — complete in p50 0.36 ms / p95 1.19 ms server time, and full materialisation in p95 2.01 ms: less than 10% of the 20 ms p95 request latency; the rest is loopback HTTP, dev-server threading and serialisation. Each request issues exactly three finds, no retries or extra commands. Within this machine, dev server and dataset, the database shows no bottleneck on the menu path; the verdict would be inconclusive at production volumes, and query growth as items scale is not ruled out.

**Q7(b) — two falsifiable hypotheses from the built MVP (400–500 words).**

*Diner hypothesis — stale-cart recovery.* **Pain:** at checkout the server revalidates every line against the current records; if a line's price changed, an item went sold out, or the stall closed after the cart was loaded, the diner is refused on the stale-cart screen (`docs/evidence/screenshots/task8-07`) and must Review or Refresh-and-retry. Who experiences it: any diner whose menu changes while they browse — the refusal names the reason, not the offending line or its fix. **Hypothesis:** showing the specific stale line with an inline one-tap fix (remove it, or keep it at the new price) would measurably speed the diner from refusal back to a paid order; the observable benefit is fewer abandoned checkouts after a stale-cart refusal. **Market and who pays:** the same situation occurs wherever menus are live and shared — hawker centres, food courts, campus dining. The rough basis is the build's own refusal modes (price change, sold-out line, closed stall), which are normal operating events rather than edge cases; no diner survey was performed, so the count is an assumption. The stall loses the sale; a platform hosting the queue would pay to keep orders completing. **Test:** the cheapest evidence is a one-screen prototype of the inline fix shown to five to ten people after they have experienced a simulated stale-cart refusal; success is the majority completing the order without leaving the screen, falsification is most saying the plain message was enough or the inline fix adding no perceived speed.

*Vendor hypothesis — no-show prediction.* **Pain:** once an order is Ready, the stall has no signal that the diner is coming; after `ready_at` + 30 minutes the only move is Mark no-show, where the payment stays paid but the prepared food is wasted (`task9-12`, `task9-14`, `task9-27`). Who experiences it: every stall, worst during the peak when a ready order idles. **Hypothesis:** a single diner-facing nudge about ten minutes after the order becomes Ready ("your order is ready — still coming?") would reduce the no-show rate; the observable benefit is fewer NoShow orders per day per stall. **Market and who pays:** the same 30-minute no-show rule exists in any pickup queue; the stall count is again an assumption (no counting was performed), and the seed's O-RO/O-N records prove the state exists, not its frequency. The stall pays through wasted food; a queue platform would pay to raise the completed-pickup rate. **Test:** the cheapest trial is a two-week instrumented A/B on one live stall — nudge on for alternate days, no-show rate compared against the stall's own baseline; success is a relative drop of at least 20% on nudge days, falsification is no difference, or complaint counts rising enough to outweigh the saved food cost.
